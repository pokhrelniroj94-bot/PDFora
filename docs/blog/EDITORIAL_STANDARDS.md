# Blog and editorial content standards

These standards govern English and Nepali editorial guides on PDFora / Niroj Tools. They are designed around Google's people-first content and Search Essentials guidance, not a target word count or a promise of rankings.

## 1. Reader value comes first

- Solve one clearly stated reader task per article.
- Explain when the method is appropriate and when it is not.
- Give complete, ordered steps that match the current live tool interface.
- Include a worked example where it materially helps; recalculate examples independently.
- Explain common errors, limitations, privacy or file-quality implications where relevant.
- Link only to relevant tools and genuinely useful related guides.
- Do not add paragraphs, FAQs, headings or keyword repetitions just to increase length. Google does not prescribe a preferred word count.

## 2. Accuracy and evidence

- Verify every tool name, route, feature, output, limit and workflow against the current product before publication.
- Cite primary sources for legal, tax, government, financial, standards, health or other consequential factual claims. Prefer the responsible government body, official standard setter or original documentation.
- Separate general explanations from current rates, fees, rules or market data. Date and re-check facts that can change.
- Do not invent test results, personal experience, user reviews, official endorsements, certifications, guarantees or statistics.
- If an article cannot be verified, qualify the statement or hold the article from indexing until it is fixed.

## 3. Titles, descriptions and structure

- Give each article a unique, concise title that accurately describes its content.
- Write a distinct summary for each article; do not use keyword-stuffed templates.
- Audit articles within the same language for repeated titles, descriptions, introductions and substantial body paragraphs. A shared subject or tool link is not automatically duplicate content, but pages targeting the same task must provide clearly different reader outcomes, examples and guidance; otherwise consolidate them rather than publishing near-identical variants.
- Do not compare a genuine Nepali translation with its English source as if it were a same-language duplicate. Keep language versions as separate URLs with reciprocal hreflang only when both main bodies are genuinely localized.
- Use one clear H1, descriptive H2 sections and meaningful link text.
- Use the reader's natural vocabulary in titles and headings without forced repetition.
- Provide a useful introduction, practical body, relevant FAQs and at least one genuinely relevant internal link.
- There is no mandatory title, description or article word count. Review snippets in context; Google may rewrite titles and descriptions.

## 4. Authorship and dates

- Display the responsible author or editorial organization on the page and use the same entity in Article structured data.
- Never invent an individual reviewer or credential. Add a named expert reviewer only after that person has actually reviewed the article.
- Display a truthful publication date and/or last-updated date. Only include datePublished when the original publication date is known. Only change dateModified after a substantive edit.
- Do not refresh dates solely to make old content look new.

## 5. Sources and links

- Add visible source links where factual claims depend on external evidence.
- Prefer stable HTTPS primary sources. Avoid tracking parameters and unrelated links.
- Use descriptive internal anchor text and verify every internal destination returns the intended page.
- Do not copy source text. Explain it in original language and add practical context for the reader.

## 6. Multilingual publication gate

- A translated page must translate the main article, headings, examples, FAQs, metadata, navigation, tool labels, validation and error states—not only the header and footer.
- Use a language-specific URL and keep the visible page predominantly in that language.
- Add reciprocal hreflang only when each listed language URL is a real, indexable equivalent. Each version must reference itself and the other available versions.
- Keep incomplete or unreviewed locales unpublished/noindex and out of sitemap/hreflang. Require native-language review before promotion.
- Preserve correct RTL rendering and test mobile layouts for Arabic and Urdu.

## 7. Indexing and technical checks

- Give each indexable article a self-referencing canonical URL.
- Include only canonical, index-eligible editorial URLs in the sitemap.
- Keep generated thin tool-guide pages noindex until their content passes the same editorial review.
- Ensure article content is server-rendered and reachable through crawlable links.
- Use BlogPosting/Article and BreadcrumbList only when the structured data matches visible content. Do not mark up invented dates, authors, sources or claims.
- FAQ text may remain visible for readers. FAQ rich results are generally limited by Google to well-known authoritative government and health sites; do not promise FAQ rich results.
- Test builds, content checks, sitemap output and representative URLs before deployment. Use Search Console URL Inspection and Rich Results Test after deployment; allow time for crawling and indexing.

## 8. Release checklist

- [ ] Tool instructions and output independently checked
- [ ] Claims and calculations verified; primary sources linked where needed
- [ ] Unique title, description, H1 and slug
- [ ] Useful, original reader-focused explanation; no arbitrary word-count target
- [ ] Internal links resolve; external references are relevant and secure
- [ ] Visible author and truthful update date
- [ ] Canonical, robots, sitemap and hreflang are correct
- [ ] Structured data matches visible page content
- [ ] Mobile and language-specific QA completed
- [ ] Content quality and production build tests pass
